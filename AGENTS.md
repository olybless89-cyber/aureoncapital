# Tesla Pro / Aureon Capital — Agent Notes

Premium membership + investment admin platform. Monorepo with pnpm workspaces.

## Quick commands

```bash
# install (pnpm 11+ via corepack, or use the pnpm binary directly)
COREPACK_ENABLE_DOWNLOAD_PROMPT=0 pnpm install

# typecheck everything (libs first, then artifacts)
pnpm run typecheck

# regenerate API clients after editing lib/api-spec/openapi.yaml
pnpm --filter @workspace/api-spec run codegen
```

## Layout

- `artifacts/api-server` — Express API (routes under `/api`): `auth`, `users`, `orders`, `stats`, `email`, `healthz`. Build: `pnpm --filter @workspace/api-server run build`.
- `artifacts/tesla-pro` — Vite + React frontend (`@workspace/tesla-pro`).
- `lib/api-spec` — OpenAPI spec + orval codegen config.
- `lib/api-zod`, `lib/api-client-react` — generated clients (do NOT hand-edit; regenerated by codegen).
- `lib/db` — Drizzle ORM schema + `drizzle-kit push`.

## Environment variables (api-server)

Set in `artifacts/api-server/.env` (gitignored — never commit real secrets). See `.env.example`:

- `DATABASE_URL` — Postgres connection string.
- `SESSION_SECRET` — JWT signing secret.
- `RESEND_API_KEY` — Resend API key. Without it, email sending is silently skipped.
- `EMAIL_FROM` — optional; defaults to the verified `Aureon Capital <noreply@swiftcargoexpressdelivery.com>`. Must use a domain verified in your Resend account. **Do not** use `onboarding@resend.dev` — that sandbox address only delivers to the account owner, so member emails would silently bounce.
- `SUPABASE_POOLER_REGION` — optional; required only when `DATABASE_URL` points at a Supabase direct host (`db.<ref>.supabase.co`). `lib/db/src/index.ts` rewrites it to the Session pooler using this region (default `eu-west-1`). Find the real region in Supabase Dashboard → Connect → Session pooler.

## Auth middleware

`artifacts/api-server/src/middlewares/auth.ts` exports `authenticate`, `requireAdmin`, and `requireSelfOrAdminBy(param)`. Applied to `users.ts`, `orders.ts`, `stats.ts`, and `email.ts`. Admin-only: user list/patch, stats, email, order PATCH, copy-trade. `GET /orders` forces non-admin callers to their own `userId`. Reuse these on any new routes — do not re-implement token parsing inline.

## Live deployment

**Everything on Railway — single service, no Vercel/Netlify.** (Prior to 2026-09-26 this was split: Railway for the API + Vercel for the frontend. That split is gone — `vercel.json` was removed from the repo root, `artifacts/tesla-pro/`, and `artifacts/tesla-pro/src/`. Do not recreate it.)

The `api-server` Express app now also serves the built frontend directly (`artifacts/api-server/src/app.ts`): after `express.static(artifacts/tesla-pro/dist/public)`, a catch-all route (`/^\/(?!api\/).*/`) serves `index.html` for any non-`/api` GET request, so client-side (wouter) routing works on refresh/deep-link. Because the frontend and API are now served from the same origin, `VITE_API_BASE_URL` should be **left unset** at build time — `main.tsx` only calls `setBaseUrl()` when it's set, so calls fall through to relative `/api/...` paths automatically. CORS in `app.ts` is now mostly vestigial (kept for local dev against other hosts) since there's no cross-origin frontend anymore.

Railpack (Railway's builder) auto-detects the workspace and uses the root `package.json` scripts: `build`=`pnpm --filter @workspace/api-server... run build && pnpm --filter @workspace/tesla-pro run build` (builds the API, then the Vite frontend into `artifacts/tesla-pro/dist/public`), `start`=`node artifacts/api-server/dist/index.mjs` (also set via `deploy.startCommand` in `railpack.json`; install step pinned to `pnpm install --no-frozen-lockfile` to avoid Railpack/pnpm config drift; `process.cwd()` at runtime is the repo root, which is how `app.ts` locates the frontend `dist/public` folder).

Railway dashboard → New project → Deploy from GitHub → pick this repo → one service (`aureoncapital-api`) serves both the app and the API at its Railway domain (custom domain `aureoncapital.com` / `www.aureoncapital.com` can be pointed at it same as before). Variables needed:

- `DATABASE_URL` — Supabase direct or pooler URL (rewritten to the `aws-1-*` pooler; see `lib/db/src/index.ts`)
- `SUPABASE_POOLER_REGION=eu-west-1` (only when the URL is a direct host)
- `SESSION_SECRET`, `SEED_ADMIN` (only `true` for first boot), optional `RESEND_API_KEY` / `EMAIL_FROM`
- Do **not** set `VITE_API_BASE_URL` (see above — leaving it unset is what makes same-origin `/api` calls work)

Railway supports IPv6, so the direct Supabase host works there — the pooler rewrite also works, harmless either way.

## Testing email locally

1. Start Postgres + the API (see "Running locally" below).
2. From the admin **Email Center** (`/admin/email`), use the **Email Service Test** card to send a test email (defaults to the admin's own address, or enter any recipient).
3. Or call the endpoint directly:
   ```bash
   curl -X POST http://localhost:8080/api/admin/email/test \
     -H "Content-Type: application/json" \
     -H "Authorization: Bearer $TOKEN" \
     -d '{"to":"you@example.com"}'
   ```
   A `{ sent, to, id }` response means Resend accepted the message.

Other email endpoints: `POST /api/admin/email/single` (`{ userId, subject, message }`) and `POST /api/admin/email/bulk` (`{ subject, message, userIds }` — omit `userIds` to send to all). On registration, a welcome email is also sent via `lib/email.ts`.

## Running locally

```bash
# 1. Postgres (Debian/Ubuntu)
sudo pg_ctlcluster 17 main start
sudo -u postgres psql -c "CREATE DATABASE stocktrade; CREATE USER appuser WITH PASSWORD 'apppass'; GRANT ALL PRIVILEGES ON DATABASE stocktrade TO appuser;"
sudo -u postgres psql -d stocktrade -c "GRANT ALL ON SCHEMA public TO appuser;"

# 2. Push schema
DATABASE_URL=postgresql://appuser:apppass@localhost:5432/stocktrade pnpm --filter @workspace/db run push

# 3. Build + run API
export DATABASE_URL=postgresql://appuser:apppass@localhost:5432/stocktrade
export RESEND_API_KEY=... EMAIL_FROM="Aureon Capital <noreply@swiftcargoexpressdelivery.com>"
export SESSION_SECRET=$(openssl rand -base64 32) PORT=8080
pnpm --filter @workspace/api-server run build && node artifacts/api-server/dist/index.mjs
```

## Login flows

- **Admin**: `admin@aureoncapital.com` / `Aureon2026!`. On startup, `index.ts` re-upserts this account with `must_change_password = true`. First login returns `mustChangePassword: true` → `Login.tsx` redirects to `/change-password` → after setting a new password the flag clears and the admin lands on `/dashboard`.
- **User**: self-registers at `/register` (free; collects `phone`). New users start `status: "pending"` → after login, `AppLayout` shows a pending-approval gate until an admin sets `status: "active"` via Admin > Users. Once active they reach `/dashboard`.


Auth token is stored under `tesla_token` in `localStorage` (`lib/auth.ts`).
## Local dev gotchas (learned 2026-08)

- `lib/db/src/index.ts` skips SSL when `DATABASE_URL` points at localhost/127.0.0.1 — plain local Postgres has no SSL and otherwise fails with "The server does not support SSL connections".
- API CORS allowlist includes `*.all-hands.dev` so the frontend can run on OpenHands work hosts.
- Vite dev port is fixed by `vite.config.ts` via `PORT` env (default 3000) with `strictPort: true` — CLI `--port` is ignored.
- The API re-seeds the admin (`Aureon2026!`, `must_change_password=true`) on EVERY startup, so any admin password change is reset on restart.
- Order creation body: `{ type: deposit|withdrawal|investment|purchase|copy_trade|membership_fee, description, amount }`. Copy-trade body: `{ userIds[], symbol, side: buy|sell, quantity, price }`. Order statuses: pending|confirmed|processing|delivered|cancelled.
- Supabase (project rifihczzbiwabmufpkjg, region eu-west-1) only resolves on the **aws-1-*** pooler hosts � `aws-0-*` answers "tenant/user ... not found". `resolveConnectionString` rewrites direct URLs to `aws-1-<region>` by default; override with `SUPABASE_POOLER_HOST` for legacy projects. The Drizzle schema (`users`, `orders`) was pushed manually via SQL because `drizzle-kit push` hits an unanswerable interactive schema-conflict prompt on this multi-schema project. (Not used by the Aureon Capital fork's own Postgres — `resolveConnectionString` is a no-op for a plain Railway `DATABASE_URL`, it only rewrites the Supabase direct-host pattern.)

## Aureon Capital fork — new features (2026-09-25)

Forked from the `stockinvestmenttrading` repo and rebranded. No backend schema/route/codegen changes were needed for either feature below — both reuse the existing generic `orders` table (`type`, `description`, `amount`, `status`) and are reconstructed purely from order `description` text on the frontend:

- **Two-tier membership** (`artifacts/tesla-pro/src/lib/payments.ts` → `MEMBERSHIP_TIERS`): Standard ($99) and Premium ($2,500). `MembershipGate.tsx` lets the user pick a tier; both create a `membership_fee` order (amount = tier price) which flips the account to `status:"active"` once an admin confirms it — same as before, just parameterized by tier.
- **Tesla Showroom installment plans** (`artifacts/tesla-pro/src/pages/Showroom.tsx` + `Orders.tsx`): at checkout, "Installment Plan" lets the buyer pick a term (3/6/12/24 months) and pay a down payment now; the down-payment order's `description` encodes the plan (model, total, months, per-month amount) in a fixed, regex-parseable format. `Orders.tsx` (`buildInstallmentPlans`) reconstructs each plan from the buyer's own orders, shows progress, and lets them submit each subsequent monthly payment (gated on the prior one being admin-confirmed) as a new `purchase` order referencing the down-payment order's id. If you change the down-payment description string in `Showroom.tsx`, update `DOWN_PAYMENT_RE`/`INSTALLMENT_PART_RE` in `Orders.tsx` to match.
